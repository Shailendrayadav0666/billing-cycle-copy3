# Story 1.1 - Upgrade CTA & Confirmation Modal

## Application Overview

StreamPlex Billing page (React SPA served at http://127.0.0.1:5173). A logged-in Standard-plan user (tpg@example.com, seeded via tests/e2e/seed.spec.ts) sees an "Upgrade to Premium" CTA on the Billing page. Clicking it opens a confirmation modal (role="dialog", data-testid landmarks: billing-upgrade-cta-button, upgrade-modal-confirm-button, upgrade-modal-cancel-button) that shows prorated pricing copy, a benefits list, and Confirm/Cancel actions. The page calls GET /api/billing?email=<value> on load (implemented, 200) and POST /api/billing/upgrade (NOT YET IMPLEMENTED — currently returns a non-2xx error such as 404/405) when Confirm is clicked. Remaining-days and prorated-charge figures are computed client-side (src/frontend/src/utils/proration.js) from the API's renew_at field relative to the real current date, using a fixed 30-day cycle, Standard price $20 and Premium price $40. Because renew_at drives these numbers and the real system date advances daily, tests that assert the story's exact figures (15 days remaining / $10.00 charge) MUST mock/intercept the GET /api/billing* response so renew_at resolves deterministically to "now + 15 days", rather than relying on the live seeded backend data. All route interception must use a wildcard-suffixed glob (e.g. '**/api/billing*') because the GET call always carries a query string.

#### 1.2. TC-E2E-02 - Clicking the CTA opens the confirmation modal with correct copy and amounts

**File:** `tests/e2e/story-1.1-upgrade-cta-confirmation-modal.spec.ts`

**Steps:**
  1. Before navigating/interacting, intercept GET '**/api/billing*' and fulfill it with a JSON body representing a Standard-plan user whose renew_at is exactly 15 days from the current date (computed at test run time, formatted as a JS-Date-parsable string e.g. 'Oct 08, 2026'), price '$20/month', plan_name 'Standard', plus minimal valid 'usages' and 'included_usage' fields so the page renders without error. This guarantees a 30-day cycle with 15 remaining days regardless of the real calendar date.
    - expect: The mocked billing data is returned to the page instead of the live backend response
  2. Reload/navigate to /billing so the page re-fetches billing data via the mock, then wait for the 'Plan & Billing' heading and 'Current plan: Standard' text to be visible (loading finished).
    - expect: Billing page is fully loaded with mocked data (no 'Loading billing...' text remains)
  3. Click the 'Upgrade to Premium' button (data-testid='billing-upgrade-cta-button').
    - expect: A dialog (role='dialog', aria-modal='true') becomes visible
  4. Read the modal's title element (id='upgrade-modal-title', an h3).
    - expect: Modal title text is exactly 'Upgrade to Premium'
  5. Read the modal body copy paragraph (class 'modal-body').
    - expect: Body copy text is exactly "Premium is $40/month. You'll be charged a prorated amount for the rest of this cycle."
  6. Read the two rows inside the modal's info box (class 'modal-info-box'): the 'Remaining days' row and the 'Charge today' row.
    - expect: 'Remaining days' row's value reads '15 days'
    - expect: 'Charge today' row's value (class 'modal-info-value') reads '$10.00' (computed as (40-20) x 15/30 = 10.00)

#### 1.6. TC-E2E-06 - Confirm button disables immediately to block a duplicate submission

**File:** `tests/e2e/story-1.1-upgrade-cta-confirmation-modal.spec.ts`

Click the Confirm button (data-testid='upgrade-modal-confirm-button') once, then, without awaiting any navigation or response, immediately (synchronously in the next step, before the POST /api/billing/upgrade response can arrive) query and click the same button locator a second time; wrap the second click attempt so a 'button is disabled' / actionability-timeout error does not fail the test (e.g. attempt the click with a very short timeout and treat a timeout/disabled-element error as an acceptable outcome, or first assert `isDisabled()` and only attempt the click via `{ force: true }` while separately asserting the element's disabled attribute).

  3. After the in-flight request settles, inspect the request counter for '**/api/billing/upgrade'.
    - expect: Exactly 1 request was made to POST /api/billing/upgrade — the rapid second click did not trigger a second request
    - expect: No assertion is made on the response body or on any success outcome for this endpoint; a non-2xx status (e.g. 404 or 405) is acceptable and expected since the endpoint is not yet implemented
